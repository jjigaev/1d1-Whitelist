# 1d1-Whitelist
Внутренняя CRM для учёта организаций, звонков и встреч на Django и Django REST Framework.

API поддерживает создание и список организаций, регистрацию звонков, назначение,
перенос и отмену встреч и расписание менеджера. Все маршруты работают без завершающего
слеша.

## Требования

- Python **3.12** с pip и venv.
- SQLite из стандартной библиотеки Python; отдельный сервер БД не нужен.
- Точные версии Django 5.2, DRF, tzdata и их зависимостей указаны в `requirements.txt`.
- `tzdata` обеспечивает работу `ZoneInfo("Asia/Almaty")`, в том числе на Windows.

## Установка и запуск: Windows PowerShell

Клонируйте полученный репозиторий (`git clone <адрес-репозитория> 1d1-Whitelist`)
или распакуйте архив. Выполните команды в корне чистой копии, где находится
`manage.py`. Команда `python --version` должна показать `Python 3.12.x`. Если в
`PATH` доступна другая версия, используйте полный путь к `python.exe` версии 3.12
в команде создания окружения.

```powershell
python --version
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe manage.py run_demo
```

Команды используют интерпретатор виртуального окружения напрямую.

## Установка и запуск: Linux / macOS

Выполните команды из корня репозитория:

```bash
python3.12 --version
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python manage.py run_demo
```

На Linux модуль venv иногда устанавливается отдельным пакетом `python3.12-venv`.

`run_demo` применяет миграции, добавляет демонстрационных менеджеров и запускает
сервер разработки на `http://127.0.0.1:8000`. Для остановки нажмите `Ctrl+C`.
Обязательных переменных окружения нет. `DJANGO_SECRET_KEY` при необходимости
переопределяет ключ для локальной разработки (`DEBUG=True`).

## Миграции и демонстрационные данные

`migrate` создаёт локальный файл `db.sqlite3` и применяет миграции.
`seed_demo` создаёт менеджеров `Demo Manager 1` и `Demo Manager 2`.
Повторный запуск использует существующих менеджеров с этими именами, не очищает БД
и не создаёт организации, звонки или встречи. Имена менеджеров не уникальны в модели;
команда предназначена для последовательного запуска при подготовке демо.

После изменения моделей новые миграции создаются через `manage.py makemigrations`.
Чтобы проверить, что существующие миграции соответствуют моделям, используйте
`manage.py makemigrations --check --dry-run`.

## Ручная проверка API

Оставьте сервер запущенным и откройте второй терминал в корне проекта. Узнайте ID
демонстрационных менеджеров, созданных командой `run_demo`.

```powershell
.\.venv\Scripts\python.exe manage.py shell -c "from crm.models import Manager; print(list(Manager.objects.order_by('id').values_list('id', 'name')))"
```

Команда ниже печатает даты для ближайшего буднего дня после сегодняшнего по Алматы.
Скопируйте три строки с переменными в начало `requests.http`. Если эти слоты заняты,
выберите два свободных на одном будущем буднем дне. Местное начало каждого слота
должно быть между 09:00 и 17:00 включительно. В `starts_at` и `rescheduled_starts_at`
укажите начало в UTC с `Z`, а в `schedule_date` — дату по Алматы.

```powershell
.\.venv\Scripts\python.exe -c "
from datetime import UTC, datetime, time, timedelta
from zoneinfo import ZoneInfo

almaty = ZoneInfo('Asia/Almaty')
day = datetime.now(almaty).date() + timedelta(days=1)
while day.weekday() >= 5:
    day += timedelta(days=1)

for key, hour in [('starts_at', 10), ('rescheduled_starts_at', 11)]:
    start = datetime.combine(day, time(hour), tzinfo=almaty).astimezone(UTC)
    stamp = start.isoformat().replace('+00:00', 'Z')
    print(f'@{key} = {stamp}')
print(f'@schedule_date = {day.isoformat()}')
"
```

На Linux/macOS замените `.\.venv\Scripts\python.exe` на `.venv/bin/python`.
Выполняйте запросы из `requests.http` по порядку. Подставьте `manager_id` из вывода
Django shell, `company_id` из поля `id` ответа `POST /companies` и `meeting_id` из
поля `id` ответа `POST /meetings`. После переноса `starts_at` должен измениться,
а `original_starts_at` остаться прежним. После отмены эта встреча должна исчезнуть
из расписания, а организация остаться в списке со статусом `meeting_set`.

## Организации

`POST /companies` принимает `name`, `bin` и `phone`. Успешный ответ `201` содержит
эти поля, `id`, `status` (`new`) и `created_at`. БИН передаётся строкой из 12
ASCII-цифр, поэтому ведущие нули сохраняются. При дубликате возвращается `400` с
ошибкой по `bin`. Если дубликат появляется после проверки сериализатора, вставку
отклоняет ограничение `UNIQUE` в SQLite, и API также возвращает ошибку по `bin`.
Распознанная блокировка SQLite при проверке БИН или попытке записи возвращает `503`.

`GET /companies` возвращает `count`, `next`, `previous` и `results`. Записи
отсортированы по `id`, на странице до 20 записей. Параметр `page` выбирает страницу.
Необязательный фильтр `status` принимает `new`, `no_answer`, `refused` или
`meeting_set`. Пустой или неизвестный статус возвращает `400`.

## Назначение встречи

Отправьте JSON на `POST /meetings`. Используйте ID существующих организации и
менеджера и выберите будущий рабочий слот.

```json
{
  "company_id": 1,
  "manager_id": 1,
  "starts_at": "{{starts_at}}"
}
```

При успехе сервер возвращает `201 Created` и JSON с полями `id`, `company_id`,
`manager_id`, `starts_at`, `ends_at`, `original_starts_at`, `status` и `created_at`.
Клиент задаёт только два ID и `starts_at`. Переданные поля ответа, которые заполняет
сервер, игнорируются. Конец наступает через 60 минут, исходное начало равно `starts_at`,
статус новой встречи — `scheduled`. Назначение встречи оставляет статус организации
прежним и не создаёт звонок.

Входное время должно быть в будущем. Используйте ISO 8601 с разделителем `T`
и окончанием `Z` или `+00:00`. Ответ всегда выдаёт время в UTC с `Z`. Сервис переводит
начало и конец в `Asia/Almaty` для проверки полного интервала с 09:00 до 18:00
с понедельника по пятницу. Для менеджера соседние интервалы допустимы. Организация может иметь
только одну встречу со статусом `scheduled`, конец которой позже текущего времени.
Отменённая встреча освобождает слот.

| HTTP | Причина |
| --- | --- |
| `400` | Некорректные поля, дата, смещение, прошедшее или нерабочее время. Ошибка привязана к полю, например `starts_at`. |
| `404` | Организация или менеджер не найдены. |
| `409` | У менеджера есть пересекающаяся встреча или у организации уже есть активная встреча. |
| `503` | SQLite не смог получить блокировку. Запрос можно повторить позже. |

Ответы `404`, `409` и `503` содержат поле `detail` в формате DRF. Сервис проверяет
наличие записей, конфликты и сохраняет встречу в одной транзакции. SQLite начинает её
в режиме `IMMEDIATE`. Для ожидания блокировки настроен `timeout=5` секунд. Сервис
преобразует распознанные ошибки блокировки в `503` после выхода из транзакции.

## Перенос и отмена встречи

`PATCH /meetings/{id}` принимает ровно одно действие. Передайте `{"starts_at":
"{{rescheduled_starts_at}}"}` с новым временем в UTC для переноса или
`{"status": "cancelled"}` для отмены.
Пустой запрос, два действия или дополнительные поля, включая `company_id` и
`manager_id`, возвращают `400`. Неизвестный ID возвращает `404`. При успехе `200`
содержит встречу в том же формате, что `POST /meetings`.

Менять можно встречу, которая ещё не началась. Перенос отменённой встречи и изменение
уже начавшейся встречи возвращают `409`. Повторная отмена возвращает `200` даже после
того, как запланированное время прошло. При переносе `original_starts_at` и `created_at`
сохраняются. Если новый слот занят, сервис возвращает `409` и сохраняет старый слот.
Отмена оставляет встречу и связанные звонки в базе и освобождает слот.

## Регистрация звонка

`POST /calls` принимает `company_id`, `result` и необязательный `meeting_id`.
Успешный ответ `201` содержит `id`, `company_id`, `result`, `meeting_id` и
`created_at`. Неизвестная организация возвращает `404`.

Для `meeting_set` нужна существующая встреча той же организации со статусом
`scheduled` и `ends_at` строго позже текущего времени. Уже начавшаяся встреча подходит,
пока она не закончилась. Для `no_answer` и `refused` поле `meeting_id` нужно опустить
или передать `null`. Недопустимая ссылка возвращает `400` с ошибкой по `meeting_id`.

Проверка встречи, создание звонка и обновление статуса организации выполняются в
одной транзакции. Распознанная блокировка SQLite возвращает `503` после выхода из
транзакции. Статус отражает последний зарегистрированный звонок. Отмена встречи
сохраняет ссылку в старом звонке и не меняет статус организации.

## Расписание менеджера

`GET /managers/{id}/schedule?date=YYYY-MM-DD` возвращает список встреч менеджера.
Дата обязательна и обозначает календарный день в `Asia/Almaty`. В список попадают
встречи с началом от местной полуночи включительно до следующей местной полуночи
исключительно. Встречи отсортированы по `starts_at`, затем по `id`. Отменённые
исключаются, завершившиеся остаются. Все времена в ответе представлены в UTC с `Z`.
Для существующего менеджера без встреч ответ `200` содержит `[]`. Некорректная дата
возвращает `400`, неизвестный менеджер — `404`.

## Модели и текущие ограничения

- `Company` — организация: название, уникальный БИН, телефон, статус и время создания.
- `Manager` — менеджер с именем; уникальность имени не требуется.
- `Meeting` — встреча одной организации с одним менеджером.
- `Call` — звонок организации с результатом и необязательной ссылкой на встречу.

Все внешние ключи используют `PROTECT`: Django запрещает удалять объекты,
на которые ссылаются встречи или звонки. База данных хранит внешние ключи,
уникальный БИН и ограничение `ends_at > starts_at`.

БИН хранится строкой, поэтому ведущие нули сохраняются. Валидатор модели требует
ровно 12 ASCII-цифр (`[0-9]`), и сериализатор явно применяет этот валидатор при
создании организации. Django не вызывает `full_clean()` автоматически при `save()`.
`TextChoices` также задаёт варианты на уровне Django, а не отдельный CHECK в БД.
Телефон — обычная строка без строгого валидатора формата.

`starts_at` — текущее запланированное начало встречи, `original_starts_at` —
первоначально запланированное начало, `created_at` — время создания записи.
Поля `starts_at`, `ends_at` и `original_starts_at` сервис заполняет явно.
Переопределений `save()` и сигналов нет.

Включены `USE_TZ=True` и `TIME_ZONE="UTC"`. Для SQLite заданы
`transaction_mode="IMMEDIATE"` и `timeout=5`; `ATOMIC_REQUESTS` не включён.
DRF настроен на JSON-ответы и свободный доступ без аутентификации.
API-тесты используют стандартный Django test runner (`manage.py test`).

## Принятые допущения

- До звонков статус организации — `new`, затем он отражает результат последнего
  зарегистрированного звонка.
- Отмена встречи не переписывает историю звонков и статус последнего звонка.
- Перед регистрацией звонка с результатом `meeting_set` встреча создаётся отдельным
  запросом. Звонок должен ссылаться на существующую активную встречу той же организации.
- Активная встреча имеет `status=scheduled` и `ends_at` позже текущего времени.
  Она может уже идти. Перенос и отмена доступны до начала.
- У организации может быть не больше одной активной встречи независимо от менеджера
  и даты. Встречи одного менеджера не пересекаются, соседние интервалы разрешены.
- Встреча длится ровно 60 минут и целиком помещается в рабочие часы:
  понедельник–пятница, 09:00–18:00, `ZoneInfo("Asia/Almaty")`.
- Входные и выходные моменты времени — UTC ISO 8601. Параметр `date` расписания
  обозначает местный календарный день Asia/Almaty.
- Новое начало встречи строго позже текущего времени. Отмена освобождает слот.
- При переносе сохраняются `created_at` и `original_starts_at`. Промежуточные
  значения `starts_at` не сохраняются отдельными записями.
- Проверка доступности и запись встречи должны выполняться в одной короткой транзакции.
- БИН уникален и содержит ровно 12 ASCII-цифр. Менеджеры создаются демонстрационной
  командой. Для них нет API управления.

## Проверки

Для PowerShell:

```powershell
.\.venv\Scripts\python.exe manage.py check
.\.venv\Scripts\python.exe manage.py makemigrations --check --dry-run
.\.venv\Scripts\python.exe manage.py test
```

На Linux/macOS используйте `.venv/bin/python` вместо `.\.venv\Scripts\python.exe`.
Тестовый раннер создаёт отдельный файл SQLite во временной папке и удаляет его
после запуска. Тесты параллельного назначения синхронизируют старт двух запросов
с независимых подключений. Проверяются два конфликта, один слот менеджера и две
активные встречи организации на разные даты. В каждом случае ожидаются `201`,
`409` и одна встреча. Длительность ожидания блокировки эти тесты не измеряют.
Отдельный тест удерживает реальную блокировку SQLite и проверяет `503` для
`POST /calls` и `POST /companies`.

Запуск из чистой копии с пустой БД проверен на Windows (сборка 26300, PowerShell,
Python 3.12.10). Команда `run_demo` применила миграции, создала двух менеджеров и
запустила сервер. Все восемь запросов из `requests.http` вернули ожидаемые статусы,
исходное время сохранилось при переносе, отменённая встреча исчезла из расписания.
Проверка Django, проверка миграций и все 40 тестов прошли в той же копии. Команды
для Linux и macOS приведены для справки. На этих системах запуск не проверялся.
